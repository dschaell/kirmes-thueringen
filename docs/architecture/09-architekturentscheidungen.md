# 9. Architekturentscheidungen

Kurzform (ADR-light). Neue Entscheidungen werden hier angehängt, nie umgeschrieben.

| ADR | Entscheidung                                                                | Begründung                                                                                                                                   | Verworfene Alternativen                                                                            |
| --- | --------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------- |
| 001 | **TypeScript in allen Schichten**                                           | Eine Sprache, geteilte Typen, geringerer Einarbeitungsaufwand für Ehrenamtliche                                                              | Java/Spring (schwergewichtig), Python (zweite Sprache neben Frontend)                              |
| 002 | **Clean Architecture mit framework-freiem Core-Paket**                      | Fachregeln testbar ohne DB; Frameworks austauschbar                                                                                          | Fastify-Handler mit eingebetteter Logik (schnell, aber schwer testbar)                             |
| 003 | **Kein ORM, statisches SQL mit `pg`**                                       | SQL ist sichtbar, reviewbar und durch Semgrep prüfbar; keine Magie                                                                           | Prisma/TypeORM (Abstraktion verdeckt Abfragen und Indexnutzung)                                    |
| 004 | **Optionale Filter über `cardinality($n) = 0` statt dynamischem SQL**       | SQL bleibt eine Konstante → strukturell keine Injection                                                                                      | Query-Builder mit String-Verkettung                                                                |
| 005 | **PostGIS `geography(Point, 4326)`**                                        | Umkreissuche in Metern, GiST-Index, Standard-Koordinaten von OSM                                                                             | Lat/Lon als zwei `numeric`-Spalten                                                                 |
| 006 | **Statisches Frontend (Astro) + JSON-API**                                  | SEO pro Ort, schnell, CDN-fähig; Interaktivität nur wo nötig                                                                                 | SPA (schlechtere Auffindbarkeit), SSR-Server (mehr Betrieb)                                        |
| 007 | **Semgrep statt CodeQL als SAST**                                           | Eigene, verständliche Regeln (pg-Injection, Schichtgrenzen) im Repo                                                                          | Nur CodeQL (eigene Regeln aufwendiger)                                                             |
| 008 | **Ersatz für „p/security-policy“**                                          | Dieses Semgrep-Regelset existiert nicht (HTTP 404); ersetzt durch `p/security-audit` + `p/sql-injection` + `p/owasp-top-ten` + eigene Regeln | –                                                                                                  |
| 009 | **Termindaten nicht im öffentlichen Repo**                                  | Zustimmung des bisherigen Betreibers steht aus; CI nutzt Beispieldaten                                                                       | Daten committen                                                                                    |
| 010 | **Server-Rendering statt statischem Build; API nur intern**                 | Änderungen in der DB sind sofort sichtbar, kein Rebuild; der Browser kennt nur die Website                                                   | Statischer Build mit Rebuild je Änderung; öffentliche API mit CORS                                 |
| 011 | **Docker Compose mit Prod-Ergänzung + Caddy**                               | Lokal und Server identisch; Umzug = Backup + Restore; HTTPS ohne Handarbeit                                                                  | Kubernetes (überdimensioniert), manuelles nginx/Certbot                                            |
| 012 | **Persönlicher Bearbeitungslink statt Konten für Festplätze**               | Kirmesgesellschaften wechseln jährlich; kein Passwort-Management, trotzdem nur für den eigenen Ort berechtigt, widerrufbar und protokolliert | Öffentliches Vorschlagsformular mit Freigabe (mehr Redaktionsaufwand), Konten mit Login (Issue #1) |
| 013 | **Routen per Link zu Google Maps / Apple Karten statt eingebetteter Karte** | Keine Drittanbieter-Daten beim bloßen Seitenaufruf (DSGVO), Navigation in der App, die Besucher ohnehin nutzen                               | Eingebettete Karte mit Einwilligungsbanner                                                         |
